# La version web n'est éprouvée ni dans Safari, ni dans Firefox, ni sur un Mac

## Constat

Le prototype de #347 vit sur lumiel, dans `out/347/` du worktree lancement. Toutes ses mesures sont faites dans le Chrome de Playwright sous Linux, sans carte graphique : décodage et encodage logiciels.

Ce qui n'est pas éprouvé :

- **Safari** : WebCodecs vidéo depuis 16.4, avec le H.264 par VideoToolbox ; wasm SIMD depuis 16.4 ; threads wasm depuis 15.2. Le décodage y sera sans doute matériel, et l'image peut y sortir en NV12 plutôt qu'en I420. Les limites de mémoire sont plus serrées.
- **Firefox** : WebCodecs vidéo sur ordinateur depuis la version 130. Son encodeur H.264 dépend de la plateforme : c'est le seul obstacle qui pourrait bloquer.
- **Mac** : l'extrait encodé par le navigateur (`browser-clip.mp4`) dans QuickTime et VLC, et le zip (`batdetect.zip`) dans l'Utilitaire d'archive.

Les fichiers et un banc à ouvrir dans Safari sont préparés dans `/Users/zaratan/Projects/dvr-wt/rapports/347/`, avec un README.

## À faire

- Rejouer le banc dans Safari, et dans Chrome sur le Mac : décodage seul et empreintes, détection sur un fil, détection sur threads, encodeurs disponibles et vitesse d'encodage.
- Rejouer le même banc dans Firefox, sous Linux et sur le Mac.
- Ouvrir l'extrait dans QuickTime et dans VLC, image par image.
- Dézipper le zip par l'Utilitaire d'archive, puis ouvrir la page dézippée dans Safari et y noter un verdict.

## Critères

- Pour chaque navigateur : les empreintes des 1 230 images comparées à FFmpeg, les détections comparées au binaire, les temps, et la liste des encodeurs H.264, notés dans docs/09.
- Chaque obstacle trouvé est classé bloquant, contournable ou de confort, et un obstacle bloquant devient une issue.
- La décision sur les navigateurs pris en charge par la version web est prise par l'utilisateur.
